# v0.4 walkthrough

v0.3 made matches arrive on their own. The output still waited for the
player to come and look: the Friday brief sat on a web page, and the
progress page gave numbers per match but not a direction. v0.4 brings the
coach to the player: the brief arrives in Telegram when it is ready, and
each mistake shows at a glance whether it is going up or down.

## What changed

1. **The weekly brief in Telegram** ([ADR 13](decisions/0013-telegram-briefs.md)).
   With `CSDC_TELEGRAM_TOKEN` set, the home page has a "Connect Telegram"
   button. It makes a one-time code (only its hash is stored, valid for 15
   minutes) and opens `t.me/<bot>?start=<code>`; pressing Start in Telegram
   links that chat to the account. When a brief becomes ready, the api sends
   the period, each player's focus titles, the team's, and a link to the
   brief, where the reasons, evidence and drills stay behind sign-in.
   `/stop` in the chat, or the button on the site, unlinks it.
2. **No webhook.** The api long-polls the Bot API, so the server got no new
   public route and the reverse proxy is unchanged. If Telegram is not
   reachable when the api starts, the site starts anyway and the button
   appears once the bot has answered.
3. **Delivery that survives a slow worker.** Briefs get a `ready_at` time
   when the coach finishes them. Delivery is a sweep every minute over ready,
   unsent briefs from the last two days, counted from `ready_at`, because
   the home worker may be off for a weekend. Briefs that became ready before
   the chat was linked are not sent, so linking does not replay history.
4. **Trend chart per mistake.** The progress page has a small line for each
   mistake: the player's rate over every three matches in a row (the same
   window as "Recent"), against the lobby's (dashed), with a dotted mark
   where practice on that mistake started. The line starts at the first full
   window, so one wild first match does not open it. It is inline SVG drawn
   on the server, so the pages still have no JavaScript.

## Running it

```bash
# Once: create a bot with @BotFather and put its token in the api's environment
CSDC_TELEGRAM_TOKEN=123456:ABC... go run ./cmd/api
# Then on the site: home page → Connect Telegram → Start in the chat
```

## Problems worth noting

- **Queued is not ready.** The first version counted a brief's age from
  when it was queued. The planner queues Friday's brief at 15:00, but a
  home worker that is off until Monday finishes it 66 hours later, past the
  48-hour cutoff, so it would never be sent. A brief queued just before the
  user linked Telegram, and finished after, was skipped for the same reason.
  Both now use `ready_at`.
- **One failed request at start turned the feature off.** Checking the token
  once at start meant a network blip during a deploy disabled Telegram until
  the next deploy. The bot now retries with backoff and the web side reads
  its username lazily.
- **Retrying what cannot succeed.** Only a 403 was treated as final, so a
  deleted chat ("chat not found") or a rejected message would have been
  retried every minute for two days. Gone chats are now unlinked, other
  4xx errors are logged once and marked, and only network errors and flood
  control are retried.
- **Groups.** The bot is for private chats, but added to a group it would
  have answered every message, including the "bot was added" notice. It now
  answers only commands there, and only to say it works in private chats.
- **A chart that disagreed with the table.** The first chart's tooltip said
  "last 3 matches" for a point that could be older (windows with no chances
  are skipped), began with single-match rates, and drew a practice mark at
  its left edge when practice started before any plotted match. Tooltips now
  name the date each window ends on, the line starts at a full window, and
  the mark appears only when there is a "before" to compare.
- **Message length.** Telegram counts 4096 UTF-16 code units, not
  characters, so the cut is done in UTF-16 units: emoji in names count
  double.

## Tests

- The Bot API client against a fake server: the token never appears in
  errors, a 403 or "chat not found" means the chat is gone, and other
  refusals are typed so the bot can tell final from passing.
- Linking against a real Postgres: a code works once, expired codes do not
  link, a chat linked by another account moves there, `/stop` unlinks, and
  group chats are ignored except for commands.
- Delivery: an old brief is not sent after linking, a queued brief is not
  sent, a brief is sent once, a blocked or deleted chat is unlinked, a final
  refusal is not retried, and flood control is.
- The home page offers Connect, the redirect carries a code the bot accepts,
  and Disconnect removes the link.
- Trend: rolling rates skip matches with no chances, and the chart is
  well-formed SVG with the practice mark in the right place.

## Known limits

- Only the brief's owner gets the message; teammates without an account do
  not. One api instance polls Telegram; a second one would need a lock.
- The trend uses a three-match window: on a handful of matches it shows a
  direction, not proof, next to the numbers that back it.
