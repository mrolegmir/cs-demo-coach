# v0.3 walkthrough

v0.2 made the service usable by a party, but every match still meant
uploading a 300 MB file by hand, and the coach had no idea what anyone did
between matches. v0.3 removes the upload step and closes the loop on
practice: log a drill, and the numbers say whether it works.

## What changed

1. **Auto-upload from the replays folder** ([ADR 9](decisions/0009-auto-import.md)).
   `csdc watch` runs on the player's PC. They press Download in CS2, the game
   saves the demo, and the watcher uploads it once the file stops growing. It
   finds the folder through Steam's library list, remembers what it uploaded
   across restarts, and skips the backlog on the first run so it does not use
   up the week's quota on old matches.
2. **Upload tokens and a public upload API.** `POST /api/demos` takes the raw
   demo with a per-user bearer token from the new Auto-upload page. Only the
   token's hash is stored, it is shown once and can be revoked, and uploads
   count against the owner's quota like browser uploads.
3. **Dedupe and real match dates.** Matches store the demo's SHA-256, so the
   same file from the watcher and the browser becomes one match. A failed
   match gives up its hash, so a fixed parser bug does not lock a demo out
   forever. The watcher also sends the file's time, so history and briefs
   order matches by when they were played, not when they were uploaded.
4. **Practice log** ([ADR 10](decisions/0010-practice-log.md)). On their own
   progress page a player logs what they practiced, for which mistake and for
   how long. Only they see the notes.
5. **"Is the drill working?" computed, not guessed.** For each mistake with
   practice, history splits the matches at the first session and compares the
   player's gap to the lobby before and after. The verdict is one of four:
   working, no change yet, too early (fewer than three matches since), or no
   baseline (practice started before the first analyzed match). The progress
   page shows it; the weekly brief hands the numbers and the verdict to the
   coach, which has to stick to them.
6. **Steam match history** ([ADR 11](decisions/0011-share-code-polling.md)).
   With `CSDC_STEAM_API_KEY` set, the Auto-upload page takes the player's
   match history auth code and newest share code, and the api walks
   `GetNextMatchSharingCode` every 30 minutes, listing new matches without
   opening CS2. The demo download for those codes is the bot step; the codes
   wait in `share_codes` until then. Share codes are decoded and validated
   locally (`internal/sharecode`), and Steam's 403 is told apart from a bad
   API key, so a revoked server key never disables everyone's link.
7. **The share-code bot** ([ADR 12](decisions/0012-share-code-bot.md)). A
   small Node.js process (`bot/`) signs in to a dedicated Steam account,
   asks the CS2 Game Coordinator for each waiting code's demo URL and reports
   it to the api, which downloads the `.dem.bz2` from Valve, unpacks it while
   streaming and imports it through the upload path (dedupe, quota, detect
   job). Codes move through a `SKIP LOCKED` queue with takeover of stale
   claims, and the api only fetches from `*.valve.net`. Go has no maintained
   Steam client library for the post-2023 sign-in, so this one piece is
   Node; the contract is three HTTP endpoints.

## Running it

```bash
# On the site: Auto-upload → Create an upload token
CSDC_API_URL=https://csdc.example.com CSDC_UPLOAD_TOKEN=... go run ./cmd/csdc watch
go run ./cmd/csdc watch -all          # also upload demos already in the folder
go run ./cmd/csdc watch -dir D:\demos # watch another folder
```

`scripts/watch.ps1` keeps it running on Windows, like `scripts/worker.ps1`
does for the worker.

## Problems worth noting

- **The auto-import research spike.** Share codes are easy: one Steam Web
  API call. Turning one into a demo URL is not: it needs the Game
  Coordinator, which only talks to a logged-in Steam client, so services
  that do it run a bot account. Instead of blocking on that, v0.3 ships the
  part that works today (a folder watcher) and keeps the bot as the next
  step behind the same upload path.
- **Why the verdict compares gaps, not rates.** A player who dies alone 40%
  of the time before practice and 30% after looks better. But if their
  lobbies after the practice were easier and everyone dropped to 25%, they
  did not improve relative to the people they play with. Comparing the gap
  to the lobby filters that out.
- **What the review caught.** The first version deduped uploads forever, so
  a demo that failed on a parser bug could never be analyzed again. It also
  split practice by upload date, so a backlog uploaded after practice
  counted as "after", and it called a player who slipped from well below to
  just below the lobby "working". All three were fixed with tests. The watcher
  also had no upload timeout (one stalled connection would freeze it) and
  retried every 30 seconds while the quota was used up.

## Tests

- Watcher: a download in progress is not uploaded, restarts do not upload
  twice, rejected files are skipped, network errors are retried, uploads
  pause after the quota runs out, and a revoked token stops it.
- Upload API against a real Postgres: token auth, dedupe per user, quota,
  revoking, and that one user cannot revoke another's token.
- Practice: verdicts for working, no change, too early, no baseline, and a
  player who was fine and got worse. Notes are visible only to their owner,
  and only the brief owner's notes reach the coach.

## Known limits

- Without a linked match history, it is still one click per match in CS2.
  With one, the bot needs a machine that is on; demos older than about a
  month are gone from Valve's servers.
- A demo downloaded days after the match is dated by the download.
- Three matches is a small sample: "working" means pointing the right way,
  not proof. The page shows the rates and match count next to it.
