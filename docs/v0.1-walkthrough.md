# v0.1 walkthrough

What was built, the decisions that shaped it, and how to talk about it.

## In one paragraph

A Go service that takes a CS2 demo and tells a party of friends the one to three
things each of them should work on, with proof. Deterministic detectors find
mistakes and attach evidence (round, time, who). Each player's mistake rate is
compared with the rest of the lobby, and only statistically clear outliers
become advice. A coach, either rule-based or an LLM, writes the explanation and
drill, and a validator rejects any advice that cites the wrong evidence.
Everything runs with `docker compose up`: one API, any number of pull-based
workers, and Postgres as the only state, including the job queue.

## The pipeline

1. **Parse** (`internal/demo`): demoinfocs events become `match.Match`, plain
   data. The parser is isolated in one package
   ([ADR 1](decisions/0001-own-match-model.md)).
2. **Detect** (`internal/detect`): five detectors, seven kinds of mistakes, each
   with a denominator ("chances") so counts become rates
   ([ADR 2](decisions/0002-first-detectors.md)).
3. **Prioritize** (`internal/coach.NewInput`): rate vs. lobby rate, a binomial
   z-score, at least 3 occurrences. This is what keeps the report to 4–6 focus
   areas for a party of five.
4. **Coach** (`internal/coach`): rules or LLM behind one interface, a strict
   validator, and one retry with the errors
   ([ADR 3](decisions/0003-grounded-coaching.md)).
5. **Serve** (`internal/web`, `internal/worker`, `internal/store`): streaming
   upload → job → worker → report page. The queue uses SKIP LOCKED in Postgres,
   with retries, backoff and stale-job takeover
   ([ADR 4](decisions/0004-postgres-queue-pull-workers.md),
   [ADR 5](decisions/0005-server-rendered-ui.md)).

## How it is tested

| Layer | How |
|---|---|
| Detectors | Table tests on hand-built matches, plus golden reports on three real matches |
| Parser | Compares against committed anonymized fixtures when demos are present |
| Coach | Validator cases, rules output must pass the validator, LLM retry logic with a scripted provider, providers against `httptest` |
| Store / queue | Real Postgres, a fresh database per test, five concurrent workers never claim the same job, retry and stale takeover |
| Worker | Corrupt demo fails fast, unavailable demo is retried, coach job end-to-end, full detect on a real demo |
| Web | Upload validation, worker auth, every evidence link resolves to a findings row, party validation |

CI runs vet, golangci-lint and `go test -race` with a Postgres service.

## Things that went wrong, and what changed

Each of these ended in a measurable fix.

- **"Untraded death" was noise.** It flagged about 90% of deaths. Measuring
  showed that only 12–13% of kills in these public matches get traded at all.
  The fix split it into *isolated death* (nobody close) and *missed trade* (the
  nearest teammate within range did not swing), so the finding names who should
  act.
- **The local LLM gave wrong advice that was still grounded.** Qwen3-30B cited
  real findings but picked issues where the player was *better* than the lobby
  ("44% vs. 41%, higher"). The fix moved prioritization into code (the
  `stands_out` flag) and made the validator reject anything else. The LLM now
  explains; it does not decide what is significant.
- **Noise passed as signal.** "63% vs. 56%" and "2 of 2 flashes" were reported as
  problems. The fix replaced an ad-hoc threshold with a binomial z ≥ 1 and at
  least 3 occurrences.
- **Old demos lack events.** 2023 CS2 demos have no freeze-time-end event and
  never set the reloading flag. The fix was a fallback to the game-rules flag,
  and the reload detector was dropped rather than shipped wrong.
- **Non-deterministic output.** Parser output depended on Go map order (player
  list, inventories, flash attribution). Golden tests caught it, and the fix
  sorts everywhere output is built.
- **Failure paths found in review.** A pre-merge review found these gaps:
  - a job that crashes its worker was reclaimed forever;
  - a dropped download counted as a corrupt demo;
  - a failed coaching hid finished findings;
  - jobs had no timeouts;
  - a canceled context lost the queue bookkeeping on shutdown.

  Each fix came with a test, for example that a job taken over too often
  fails, and that failed coaching keeps the findings and can be retried.

## Design FAQ

- *Why not let the LLM do everything?* It is the most expensive part and the
  least trustworthy. Code computes the facts and the significance; the model
  only explains. The product works without it.
- *Why Postgres as a queue?* One stateful dependency at this scale. SKIP LOCKED
  gives exactly-once claiming without a broker. The concurrency test proves it.
- *Why do workers pull?* Parsing is CPU-heavy and can run on a home PC. Pulling
  needs no open ports.
- *What would you do next?* Recalibrate thresholds on real 2026 matchmaking demos.
  Then v0.2: accounts and quotas, plus issue history across matches (findings
  are already stored as rows for that) and the weekly brief.

## Known limits

- Calibrated on three public 2023 demos. Real party demos are needed.
- Distances ignore walls.
- The API keeps uploads on local disk, so it runs as a single instance.
- No authentication yet (v0.2).
